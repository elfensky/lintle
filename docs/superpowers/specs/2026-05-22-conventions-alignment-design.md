# lintle Conventions Alignment — Design

- **Date:** 2026-05-22
- **Status:** Approved; ready for implementation planning
- **Topic:** Align the implemented `lintle` project with the tooling, code-quality, test, and
  documentation conventions of the reference project `descent-engine`
  (`/Users/andrei/Developer/github/descent-engine`)

## 1. Problem statement

`lintle` is fully implemented: 789 LOC of source across seven modules, 687 LOC of tests
across seven test files, 77 passing tests. The corpus cleaner works. What it lacks is the
*project scaffolding* a mature repository carries — and the reference project
`descent-engine` is the agreed model for that scaffolding.

Concretely, `lintle` today is missing:

- **Linting/formatting** — `ruff` is not even installed; there is no `[tool.ruff]` config.
- **Coverage tooling** — no `pytest-cov`, no coverage command.
- **Project documentation** — no `README.md`, `CONTRIBUTING.md`, or `CHANGELOG.md`.
- **A current `CLAUDE.md`** — the existing one is stale: it claims "no source code exists yet,"
  which has been false since the tool was built.

This design is a **convention-alignment pass**. It changes no runtime behaviour of the tool —
no edits to validation logic, repair logic, the pipeline, or the CLI's observable behaviour.
It is additive (new config, new docs) plus two non-behavioural transforms (a `ruff`
formatting/lint pass and a test-file reorganisation).

## 2. Goal & non-goals

**Goal:** a third party opening `lintle` should find the same setup, code-quality bar, test
framework, and documentation depth they would find in `descent-engine`.

**Non-goals — explicitly excluded, with rationale:**

| Excluded | Rationale |
|----------|-----------|
| Docker (`Dockerfile`, `docker-compose.yml`) | `lintle` is a local batch CLI run against a local corpus, not a long-running service. |
| `pytest-asyncio`, `pytest-httpx` | `lintle` has no async code and makes no HTTP calls. These plugins exist in `descent-engine` only because it is a network worker. |
| Git Flow / GitHub-Issues workflow machinery | Decided: `lintle` is a focused single-purpose tool; a light process (conventional commits, feature branches) is documented instead. |
| Google-style docstrings (Args/Returns/Raises blocks) | Decided: `lintle`'s concise one-paragraph docstrings are already clear; full blocks on small pure functions add noise, not value. |
| Type hints on all signatures | `descent-engine` mandates them, but retrofitting hints onto 789 LOC is high-churn rewriting of working code. Ruff's selected rule set does not enforce them. Deferred. |

Nothing here alters how `lintle validate` or `lintle clean` behaves.

## 3. Work areas

### 3.1 Build & tooling setup — `pyproject.toml`

Add `ruff` and `pytest-cov` to the `dev` dependency group. Add two config tables copied
verbatim from `descent-engine` (adjusted only for the Python target already in use):

```toml
[tool.ruff]
target-version = "py311"
line-length = 88
src = ["src"]

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B", "SIM"]
```

Reorder the file's tables to match `descent-engine`'s layout (`build-system`, `project`,
`project.scripts`, `dependency-groups`, `tool.ruff`, `tool.ruff.lint`, `tool.pytest`). Keep
`[tool.hatch.build.targets.wheel]` — `lintle` needs it because the package directory name
does not match the distribution name; `descent-engine` can omit it because its names align.

Also add:

- `.python-version` containing `3.11` — matches `descent-engine`, pins the interpreter for `uv`.
- An empty `tests/__init__.py` — `descent-engine` has one; makes the test directory a package.

`uv.lock` will be regenerated by `uv sync` once the new dev dependencies are declared.

### 3.2 Code-quality pass

After §3.1, run `uv run ruff check .` and `uv run ruff format --check .`. Then:

- Apply `ruff format` across source and tests. Expect small whitespace/line-wrap diffs in
  most files; the existing code is already close to the 88-column target.
- Fix every `ruff check` finding. `I` (import sorting) and formatting fixes are mechanical.
  For `B` (bugbear) and `SIM` (simplify) findings, apply the fix only where it preserves
  readability — any finding whose "fix" would obscure intent is surfaced for a human call
  rather than applied blindly.

The 77 tests must still pass after this pass; this is the guardrail proving the pass was
behaviour-neutral.

### 3.3 Test reorganisation into `Test*` classes

All seven test files are reorganised so flat module-level test functions become methods of
`Test*` classes, one class per unit or behaviour under test — matching `descent-engine`'s
style (e.g. `class TestParseTLE:`).

- Test functions become methods; each gains `self` as its first parameter.
- `pytest` fixtures (`line1`, `line2`, …) continue to inject as method parameters unchanged.
- Module-level helper constants and factory functions in test files stay at module level.
- **The 77 tests, their names, and their assertions do not change** — only their grouping.

Indicative grouping for `test_tle.py`: `TestComputeChecksum`, `TestCheckColumns`,
`TestValidateBody`, `TestChecksumError`, `TestValidateLine`, `TestValidateRecord`. The
other six test files are grouped on the same principle (one class per function or
behaviour cluster). The implementation plan pins the exact class breakdown per file.

### 3.4 Documentation

| File | Action | Contents |
|------|--------|----------|
| `README.md` | new | Overview; Quick Start; Commands; Architecture (a Mermaid diagram of the `clean`/`validate` data flow, the `cli → pipeline → repair → tle` module chain, the two modes); the measured defect distribution; the four inviolable principles; tech stack. Mirrors `descent-engine`'s README shape. |
| `CONTRIBUTING.md` | new | Prerequisites (Python 3.11, `uv`); `uv sync` setup; testing + coverage commands; `ruff` usage; light git workflow (conventional commits, feature branches, semver). No Docker, env-var, or Git-Flow sections. |
| `CHANGELOG.md` | new | Keep a Changelog format. Seeded with a single `[0.1.0] - 2026-05-22` entry covering the implemented cleaner plus this tooling/docs pass. Version stays `0.1.0`. |
| `CLAUDE.md` | rewrite | Currently stale ("no source code exists yet"). Rewritten to `descent-engine`'s `CLAUDE.md` structure (tech stack, critical rules, code style, project layout, commands, working style, verification, file guidelines). **Domain content is preserved verbatim in substance:** the four inviolable principles and the corpus-handling warnings (never read a corpus file whole; `data/` is git-ignored). |
| Docstrings | gap-fill only | Keep the existing concise prose style. Only add a docstring where a public symbol lacks one. No rewriting of existing docstrings. |

## 4. Verification

Run all four, in order, and report actual output — never claim success without it:

```bash
uv run pytest                                                        # 77 pass
uv run pytest --cov=lintle --cov-report=term-missing --cov-branch    # coverage report
uv run ruff check .                                                  # no findings
uv run ruff format --check .                                         # no diff
```

No `--cov-fail-under` gate is added (matching `descent-engine`, which reports coverage but
does not enforce a threshold).

## 5. Build order

1. `pyproject.toml` + `.python-version` + `tests/__init__.py`; `uv sync` to install `ruff`
   and `pytest-cov` and refresh `uv.lock`.
2. Test reorganisation into `Test*` classes; confirm 77 still pass.
3. `ruff` code-quality pass (format + lint fixes); confirm 77 still pass.
4. Documentation: `README.md`, `CONTRIBUTING.md`, `CHANGELOG.md`, `CLAUDE.md` rewrite,
   docstring gap-fill.
5. Full verification (§4).

Steps 2 and 3 are ordered test-reorg-then-format so the formatter passes once over the final
test layout rather than twice.
